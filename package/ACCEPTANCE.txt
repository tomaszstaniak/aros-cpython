C. NETWORK AFTER A BOOT (L12), FIVE MORE BOOTS
----------------------------------------------
The installation from A, booted five more times (one cold start, four
restarts). In each boot, after 150 s: Status (is AROSTCP and its DHCP client
running), a name lookup of pypi.org, www.python.org and example.com by a
small C program through bsdsocket.library (independent of Python), the same
lookups in python followed by an HTTPS request, the same again in a second,
new interpreter, and the C lookup again.
PASS  boots 1, 3, 4, 5: DHCP client running; every lookup answered (C and
      both interpreters); HTTPS 200.
FAIL  boot 2: at the check 150 s after the boot, AROSTCP was loaded but its
      DHCP client not running, and the C program stopped with "Unable to
      open bsdsocket.library version 4 or later": the network stack was not
      available to any program. Whether it would have started later was not
      established (the requester stopped the rest of that boot's checks).
Together with the earlier boots: in 2 of 10 boots with a correct network
configuration network access failed (F3: name lookup failed for every host
for the whole boot, with no check independent of Python; boot 2 here: no
network stack at the check). The two were measured differently and are not
known to share a cause. In the 8 other boots name lookup and HTTPS worked.
See L12.

KNOWN LIMITS
------------
L1  No interruption. Ctrl-C and Break set the task's break signal; nothing
    in the interpreter turns it into KeyboardInterrupt, and time.sleep()
    does not wait for it. Recovery from a script that does not end: reboot.
L2  Sockets only in the main thread. bsdsocket.library gives each task its
    own library base and refuses calls through another task's base; this
    build opens one base, for the main task. Needs a base per thread in the
    socket, select and ssl code (and in OpenSSL's socket I/O).
L3  No processes: no fork or exec on AROS, so no subprocess, os.popen or
    multiprocessing. os.system works.
L4  Missing modules: _ctypes/ctypes, mmap, _curses/curses, readline,
    _dbm, _gdbm, _tkinter, termios (and tty, pty), resource, syslog,
    _posixsubprocess, _posixshmem, _multiprocessing, _uuid, _zstd. They are
    not replaced by stand-ins: importing them fails.
L5  pip installs pure-Python wheels only (sdists need subprocess). The
    bundled pip is changed so that it loads without mmap.
L6  No locale.gettext() and friends: the SDK's libintl and libiconv are
    LGPL and would be linked statically, so _locale is built without them.
L7  time.localtime().tm_zone is "": the C library leaves tm_zone NULL.
L8  python -u leaves the calling Shell's output unbuffered after exit, and
    the prompt's escape codes then print as text in that Shell (a C
    library behaviour, reproduced with a four-line C program). The
    launcher does not use -u.
L9  Entropy comes from CPU timing jitter (jitterentropy), as ABIv11 has no
    operating system entropy source.
L10 time_t is 32 bits in this C library.
L11 Startup needs AROSTCP running (bsdsocket.library is opened at start).
L12 The network is not always ready after a boot: in 2 of 10 test boots
    with a correct configuration network access failed, once as name lookup
    failing for every host for the whole boot, once as no network stack at
    the check 150 s after the boot (see B and C). A restart cleared it both
    times.
L13 os.stat().st_flags holds no meaningful value: the C library leaves it
    unset (measured 0x4bcaa880 on a RAM: directory). shutil.move() of a
    directory between volumes reads it as the BSD "immutable" flag and
    fails with PermissionError, so pip --target works only on the volume of
    pip's temporary directory (RAM:). The next version will not report
    st_flags.
